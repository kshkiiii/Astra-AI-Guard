# ИИ-сторож

## Эксперту: быстрый запуск

**Windows x64 и Python 3.12 x64.** Распакуйте финальный ZIP в доступную для записи
папку и дважды нажмите **START.bat**. Скрипт создаст окружение, установит закреплённые
зависимости, проверит SHA-256 всех весов и откроет интерфейс в браузере после готовности.
Остановка — `Ctrl+C` в окне сервера. API: http://127.0.0.1:8000/docs.

При клонировании репозитория модели загружает Git LFS (`git lfs install`, затем
`git clone`). При скачивании исходников ZIP скрипт запуска умеет догрузить веса
с GitHub и проверить их контрольные суммы. Для первой установки из Git нужен
интернет; готовый комплект с папкой `wheels/` устанавливается автономно.

| Команда / кнопка | Результат |
| --- | --- |
| `START.bat` | Демо и API на localhost:8000 |
| `START.bat --check-only` | Проверка файлов моделей и зависимостей |
| `START.bat --test` | Все автоматические тесты |
| `START.bat --evaluation --host 0.0.0.0` | API с неизменённой политикой организаторов |
| `BUILD.bat` | Финальная папка и ZIP в `dist/` с весами и доступными offline wheels |

Веса и CPU runtime включены в Git через LFS. Старые сборки, рабочие окружения,
журналы, личные настройки, временные файлы и `dist/` исключены из Git.

Локальный сервис проверки запросов к DevOps-ассистенту. Анализирует запрос,
историю и текстовые вложения с учётом доверенной роли пользователя и YAML-политики.
Возвращает `allow`, `confirm` или `block`, категорию риска и объяснение.

## Запуск

Windows x64, Python 3.11+, CPU. Все необходимые веса и CPU-движок должны находиться
в `artifacts/`; при переносе проекта эту папку нужно копировать вместе с исходниками.
Веса и рабочее окружение исключены из Git. При инференсе доступ к интернету не требуется.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r api/requirements.txt
.\.venv\Scripts\python.exe -m api
```

Демо: http://127.0.0.1:8000/; OpenAPI: http://127.0.0.1:8000/docs.
`GET /ready` сообщает готовность моделей и версию политики.
Для сервера с доступом по сети:

```powershell
.\.venv\Scripts\python.exe -m api --host 0.0.0.0 --port 8000
```

При запуске сервис автоматически прогревает Qwen3Guard на `127.0.0.1:18082`.
После изменения кода или конфигурации перезапустите API. Изменения через редактор политики применяются без перезапуска; при ручной правке YAML перезапуск обязателен.

## Проверка

`POST /v1/check` принимает только запрос и контекст. Роль в доверенном контексте
задаётся вызывающей интеграцией; текст запроса и вложения не назначают полномочия.

```json
{
  "user_prompt": "Перезапусти payments-api в production",
  "context": {
    "target_agent": "it_ops_agent",
    "user_role": "sre",
    "history": [],
    "attachments": []
  }
}
```

Проверка через CLI:

```powershell
.\.venv\Scripts\python.exe -X utf8 check.py --text "Покажи логи payments-api в dev" --role developer
```

`/v1/check` оценивает запрос. Передача демонстрируется отдельно в интерфейсе:
`allow` передаётся локальному адаптеру, `block` останавливает передачу,
`confirm` требует отдельного явного согласия на неизменный запрос.
Демо-профили `developer`, `sre`, `admin` выбираются в интерфейсе.
Демо-агент фиксирует получение квитанцией и не исполняет команды.

## Архитектура и политика

TF-IDF/E5-классификаторы находят угрозы и признаки действий; дообученный MiniLM
определяет область запроса; Qwen3Guard 0.6B Q8 проверяет спорное содержимое.
Цитаты, история, вложения и декодированные представления проверяются как
недоверенные данные. Все модели работают на CPU.

MiniLM хранит таблицы эмбеддингов в FP16 и переводит только выбранные строки в FP32.
Исходные значения этих таблиц точно представимы в FP16: конвертер проверяет это до
сохранения. Остальной трансформер вычисляется в FP32. Файл весов уменьшен с 427,5
до 235,1 МБ; на 340 проверках вероятности и решения совпали с исходной моделью.

Голова `mode_head` существующего семантического классификатора дообучена на
контрастных парах «обсудить / выполнить», включая запросы на действие после
теоретического вступления. Энкодер и остальные головы зафиксированы. На 64
авторских отложенных примерах точность выросла с 75% до 90,6%, на 252 прежних
контрольных примерах осталась 100%. Это синтетическая проверка, не внешний бенчмарк.
Новых зависимостей для инференса нет; суммарный рост файла классификатора после
дообучения режима и операции составляет около 3,2 КБ.
Первая оптимизация проверена в полном конвейере с настоящим модератором на 782
запросах; решения и категории совпали с исходным вариантом, ошибок инференса нет.
После дообучения удаления БД повторно проверены 282 отдельных контрольных запроса:
решения и категории также сохранены. Публичные примеры и авторские контрольные
наборы не заменяют закрытую оценку организаторов.

Запрос `удали базу данных users (dev)` распознаётся как `delete_resource` с объектом
`users`, окружением `nonprod`: `developer` получает `block`, `sre` и `admin` — `confirm`.
Голова операции дополнительно обучена на вариантах удаления БД и SQL с replay
прежних предсказаний. Изменена только строка `delete_resource`, число параметров
сохранено. Для явных команд удаления базы/таблицы/схемы проверка YAML применяется
также при ошибке нейросетевого определения операции. Объяснение команды остаётся
информационным запросом. Данные находятся в `training/database-intent/`, обучение —
`tools/train_database_intent.py`, отчёты — в `docs/verification/database-*.json`.

Права ролей, окружения и необходимость подтверждения задаются в
`security_policy.yaml`. Изменение прав применяется через редактор сразу, при ручной правке файла после перезапуска, без
переобучения. `config.yaml` содержит пути к рабочим весам и параметры инференса.
`attack_probability` — диагностический показатель детектора.

Вход ограничен 200 000 символами. Для модерации действуют дополнительные ограничения:
12 000 символов и 4096 токенов. Превышение лимита даёт `413`; недоступность,
занятость или превышение бюджета проверки — `503`, без передачи агенту.

## Журнал и настройки

Журнал доступен в интерфейсе и через `GET /v1/audit`.
SQLite-файл: `api/runtime/audit.sqlite3`. Записываются метаданные решения;
исходные запросы, история, вложения и значения секретов в журнал не сохраняются.
Каждый вызов `/v1/check` использует только переданный контекст.

| Переменная | По умолчанию |
| --- | --- |
| `GUARD_CONFIG` | `config.yaml` |
| `GUARD_AUDIT_PATH` | `api/runtime/audit.sqlite3` |
| `GUARD_CORS_ORIGINS` | пусто |
| `GUARD_DEMO_ENABLED` | `1`; значение `0` отключает передачу |

Относительные пути настроек разрешаются от корня проекта.

Источники моделей: [E5](https://huggingface.co/intfloat/multilingual-e5-small),
[MiniLM](https://huggingface.co/MoritzLaurer/multilingual-MiniLMv2-L6-mnli-xnli),
[Qwen3Guard](https://huggingface.co/Qwen/Qwen3Guard-Gen-0.6B),
[Q8 GGUF](https://huggingface.co/QuantFactory/Qwen3Guard-Gen-0.6B-GGUF).
CPU-движок — [llama.cpp](https://github.com/ggml-org/llama.cpp).

## Итоговая оценка с политикой организаторов

Исходный файл сохранён без изменений как `organizer_policy.yaml`. Для автоматической
оценки запускайте отдельный экземпляр с `config.organizer.yaml` и отключённым управлением:

```powershell
$env:GUARD_CONFIG = "config.organizer.yaml"
$env:GUARD_DEMO_ENABLED = "0"
$env:GUARD_ADMIN_TOKEN = ""
.\.venv\Scripts\python.exe -m api --host 0.0.0.0 --port 8000
```

Режим оценки — CPU-only. Все ONNX-сессии используют CPUExecutionProvider,
llama.cpp запускается с `--n-gpu-layers 0`. Итоговый сервер должен иметь не более
8 vCPU и 32 GB RAM. Конфигурация поставляется для Windows x64; для Linux требуется
подготовить соответствующий бинарный llama.cpp и изменить `moderator.binary`.
Один HTTP-ответ ограничен по объёму диагностики: проверяются все действия, в ответе
показываются первые 32, `intent_total` сообщает общее число, `details_truncated` — сокращение.

## Редактор политики и административный доступ

Вкладка «Настройка политики» показывает действующие правила, матрицу прав и версию.
Для изменения задайте отдельный случайный ключ от 24 символов и имя оператора перед запуском:

```powershell
$env:GUARD_ADMIN_TOKEN = python -c "import secrets; print(secrets.token_urlsafe(32))"
$env:GUARD_ADMIN_USER = "team-admin"
$env:GUARD_DEMO_ENABLED = "1"
$env:GUARD_CONFIG = "config.yaml"
.\.venv\Scripts\python.exe -m api
```

Введите ключ в редакторе. Он хранится в памяти вкладки и не сохраняется в браузере.
Демо-профиль `admin` не даёт доступа к редактированию. Без ключа изменение отключено.
`GET /v1/policy` возвращает активную политику, версию и ревизию; защищённые
`POST /v1/policy/validate`, `PUT /v1/policy` и `GET /v1/policy/changes` используют
`Authorization: Bearer <ключ>`. При применении сервер валидирует YAML и матрицу прав,
проверяет исходную ревизию, повышает версию, атомарно заменяет файл и активную политику.
Автор из настроек сервера и время попадают в историю изменений. Все ожидающие
подтверждения отменяются. Конфликт версий возвращает 409 без изменения правил.
Для нескольких операторов используйте отдельную доверенную авторизацию перед API;
встроенный режим рассчитан на одного оператора с именованным ключом.

Журнал фильтруется по времени, решению, категории и роли. Время в API — ISO 8601,
интерфейс переводит местное время в UTC. В таблице видна версия политики каждого решения.

## Диалоги и хранение истории

Создайте диалог в блоке «Диалоги». Роль закрепляется при создании. Реплики и объяснения
сохраняются в SQLite, доступны для просмотра, очистки и удаления после перезагрузки страницы.
Случайный HttpOnly cookie изолирует владельцев; сервер хранит его хеш. SameSite=Strict
и обязательный `X-Guard-Client: web` защищают изменяющие сессионные маршруты.
На HTTPS задайте `GUARD_COOKIE_SECURE=1`. Это изоляция демонстрационных браузерных
сессий; пользовательский логин для публичного хостинга подключается отдельно.

По умолчанию срок хранения — 24 часа с последнего изменения (`GUARD_SESSION_TTL`,
от 60 секунд до 7 суток), до 100 ходов, 100 000 символов истории и текущего запроса,
20 диалогов на владельца и 1000 на экземпляр. Истёкшие записи удаляются при обращении
к сессионному API. История не обрезается незаметно: при заполнении возвращается 413,
пользователь очищает её или создаёт новый диалог. Известные форматы токенов, ключей,
паролей в присваиваниях маскируются перед записью. Маскирование не гарантирует
распознавание произвольного секрета в свободном тексте; для демонстрации используйте
синтетические данные. Журнал решений по-прежнему не хранит тексты.

Кнопки сценариев показывают легитимное продолжение и атаку через историю.
Следующий ход проверяется отдельно, интерфейс объясняет влияние предыдущих реплик.
Сессии обслуживаются `/v1/sessions/*`; `/v1/check` сохраняет независимый режим и никогда
не подмешивает сессионную память. Очистка/удаление диалога отменяет его подтверждения.

## Проверки и сборка

```powershell
.\.venv\Scripts\python.exe -m pip install -r api/requirements-dev.txt
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -B -m unittest discover -s evaluation -v
$env:NO_PROXY = "127.0.0.1,localhost"
.\.venv\Scripts\python.exe -B tools/benchmark.py --endpoint http://127.0.0.1:8000/v1/check --output old/reports/final
.\.venv\Scripts\python.exe -B tools/package_release.py --output old/delivery/guard-checkpoint
```

Бенчмарк использует неизменённый evaluator v2, пять прогревочных запросов и последовательный
HTTP-прогон. Публичный dev содержит обучающие примеры и не является независимой оценкой.
Для CPU-бонуса жюри проверяет p95 ≤ 3 секунд, отсутствие ошибок и долю блокировок
high/critical ≥ 0,85 на своём закрытом прогоне. Локальные результаты не гарантируют бонус.
Сборка включает исходники, интерфейс, модели, токенизаторы, CPU runtime, исходную
политику, зависимости, проверки и контрольные суммы. Рабочий журнал, диалоги, ключи,
окружение, старые эксперименты в комплект не входят. Подготовка зависимостей из интернета
допустима до запуска; инференс не требует сети.

Хостинг ещё не настроен. Перед внешним доступом требуются HTTPS, ограничение доступа
к админке и пользовательская авторизация перед демо. Итоговый `/v1/check` должен
оставаться доступен организаторам от дедлайна до завершения оценки.

### Проверенный автономный комплект

Wheel-пакеты комплекта собраны для **Windows x64 и Python 3.12**.
Все 38 прямых и транзитивных зависимостей закреплены в `requirements.lock.txt`.
В чистом окружении установите их без обращения к индексам:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --no-index --find-links wheels -r requirements.lock.txt
```

Для другой версии Python подготовьте соответствующие wheel-пакеты заранее.
Python и системные Windows runtime должны быть установлены на целевой машине.
Локальная проверка чистого окружения не заменяет проверку выбранного хостинга.

### Повторение обучения и сжатия

Данные, разбиение и происхождение находятся в `training/intent/`. Семейства формулировок
не пересекаются между train, validation и test. Replay содержит только примеры,
которые действительно входили в обучение исходного классификатора; прежние исключения
по пересечению с контрольными данными сохранены. Сила регуляризации выбирается по
validation, test не участвует в выборе. Конвертация эмбеддингов требует дополнительного
`onnx` только в среде подготовки (`training/requirements-prepare.txt`).

Исходные веса для отката сохранены вне поставки в
`old/checkpoints/intent-compact-20261122/`. В рабочем каталоге можно подготовить
новых кандидатов, не заменяя активные веса:

```powershell
.\.venv\Scripts\python.exe -X utf8 -B tools/train_intent.py --source old/checkpoints/intent-compact-20261122/semantic_security.joblib --output artifacts/intent-candidate.joblib
.\.venv\Scripts\python.exe -X utf8 -B tools/train_database_intent.py --source old/checkpoints/database-intent-20261122/semantic_security.joblib --output artifacts/database-candidate.joblib
python tools/compact_context.py --source old/checkpoints/intent-compact-20261122/model.onnx --output artifacts/context-candidate.onnx
.\.venv\Scripts\python.exe -X utf8 -B tools/verify_context.py --source old/checkpoints/intent-compact-20261122/model.onnx --candidate artifacts/context-candidate.onnx
.\.venv\Scripts\python.exe -X utf8 -B tools/verify_intent_guard.py --source old/checkpoints/intent-compact-20261122/semantic_security.joblib --candidate artifacts/intent-candidate.joblib --data evaluation/dev.jsonl old/additional_datasets/semantic_v5/holdout.jsonl old/additional_datasets/semantic_v5/stress.jsonl
```

Отчёты применённых весов и контрольные суммы сохранены в `docs/verification/`.
Замеры памяти относятся к отдельному процессу контекстной модели, а не ко всему сервису.
После обновления весов перезапустите работающий API.
